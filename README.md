# MSME_Early_Warning_Intervention
## Manual assessment and per-warning recommendations ? 23 October 2026

The RM runs an assessment for a submitted completed reporting month with sufficient history. A breached result creates its warning automatically. Each newly created warning schedules one recommendation attempt; existing warnings are not scanned for generation. A failed attempt leaves RECOMMENDED_ACTION empty. In the existing recommendation screen, choose an open warning: the button reads its saved JSON, or generates and saves advice only for that warning if empty. Existing populated records are preserved, including legacy placeholder text.

Both Python services load their local .env followed by the repository-root .env; existing process environment variables take priority. The root file contains the shared Oracle/JWT settings, schema owners, local Ollama URL/model and INTERNAL_SERVICE_TOKEN. It is ignored by Git. The dashboard launcher finds the root .venv and keeps startup errors visible. Python evidence selection uses snapshot reporting periods rather than assessment creation dates.

Start the Java services separately in STS as usual. Keep Ollama running with `ollama serve` (skip this if already running); the configured model is `qwen3:1.7b`. In Recommendation-service run `..\.venv\Scripts\python.exe -X utf8 -m recommendation.serve`. In dashboard-service run `..\.venv\Scripts\python.exe -X utf8 -m dashboard.serve`, or double-click its existing start-dashboard.cmd. In frontend run `npm run dev` and open the address Vite prints. Ports remain 8085 for recommendations and 8086 for the financial dashboard. Restart affected services after loading the changes.

MS2/MS3 read the root .env from their module or repository working directory for internal calls. If warning processing is unavailable after assessment persistence, the error explicitly says the assessment was saved; running that assessment again retries warning processing without recalculating results. Existing closure and intervention policies were not changed in this update. No SQL changes, dependency installation, service launches or test/build execution were performed; only static source/configuration review and syntax/whitespace checks.

## Agreed workflow implementation - 23 October 2026 (latest)

This update supersedes earlier descriptions of empty recommendation fields and case closure:

- RM manually runs assessments for submitted completed reporting periods with three months of history. No automatic assessment execution or recalculation of saved results.
- Latest/history/comparison/previous links follow snapshot reporting periods, within the same MSME. Backfills repair links in a transaction serialized per MSME, without changing results. Green means only the latest reporting-period assessment is HEALTHY.
- New breached assessments create OPEN warnings automatically and attempt recommendation generation once. The warning CLOB contains generated JSON or exactly `reccommendation service not available`. RM (assigned businesses) and Risk Admin can view/retry the selected open warning. The marker is retryable; successful JSON is immutable. No existing-warning generation scan was added.
- A representative sees their own profile, MSME, snapshots, assessments, all threshold versions, warnings, intervention notes and analytics. Recommendation fields are omitted from their warning responses; recommendation generation and activity-history endpoints are forbidden.
- Only RM closes cases. Both the warning decision and intervention Append -> close close the warning and its intervention together, retaining history. New snapshots and follow-up dates never close cases. One intervention per warning remains enforced; legacy multiple records require manual database correction.
- Risk Admin retains administration and threshold creation. Intervention writing is advice-only, and only while the RM's intervention is escalated. Notes append; saved recommendation JSON is separate.
- Latest threshold version applies immediately; the retained STATUS/effective-date fields do not control selection. New versions preserve history and notify the assigned RM/representative.
- Current/future snapshot months are rejected. Submitted months are disabled in the entry form; completed historical months remain available. Missing/negative amounts and overdue above total are rejected. Zero receivables means no overdue breach. Positive-to-zero revenue is a 100% decline; zero-to-positive and zero-to-zero percentages are not invented. Current zero revenue is HIGH_PRIORITY, with monthly staff alerts and an early submission alert for RM.
- Main frontend login uses an HttpOnly, SameSite=Strict cookie, restored via GET /api/auth/session after refresh. Existing JWT expiry is retained. Logout expires authentication/CSRF cookies. Cookie write requests require a matching CSRF header; gateway translation keeps downstream authorization checks. Legacy bearer API clients remain supported. For HTTPS deployment, set app.auth.cookie-secure=true.
- Notifications appear globally and in the sidebar, with clickable navigation to the concerned business's threshold/history view. Displayed history is browser memory only (up to 100 entries), cleared on refresh/logout. Existing ACTIVITY_LOG records supply events; there is no notification table. Polling is every five seconds, with a session baseline rather than replaying old events. Existing staff activity histories remain protected from representatives.
- Error handling distinguishes bad input (400), authentication (401), forbidden access (403), conflicts (409), unavailable storage (503), and unexpected errors (500). Inactive MSMEs cannot receive a representative; business-active checks independently invalidate representative authentication. Existing deactivation cascade is retained.
